## 十一、踩过的坑（给要改构建 / 测试 / 降级的人）

1. **`console.log` 在 Windows 上什么都看不到。**
   Qt 的 Windows 构建是 GUI 子系统程序，没有控制台 —— 重定向到文件也是 0 字节。
   唯一可靠的回传通道是**进程退出码**，所以 `tests/` 下的冒烟测试用
   `Qt.exit(bitmask)` 上报结果，由 `tools/test.sh` 解码。
   注意 POSIX 的 `WEXITSTATUS` 只保留低 8 位：`Qt.exit(1000)` 在 bash 里读到的是
   `232`，因此每个测试文件的断言数控制在 8 条以内。
   需要把一段**文本**带回终端时，走 `Qt.createComponent(...).errorString()`
   之类的正式接口，或者干脆把文本画到窗口里抓图 —— 别指望 `console.log`。

2. **不要在 `Component.onCompleted` 里同步读 `implicitWidth`。**
   Qt Quick Layouts 把尺寸重算推迟到渲染循环的 polish 阶段。
   实测 `Slots.buttonContent` 在 `onCompleted` 时读到 `0`，下一个事件循环就是
   `94`，16ms / 200ms 后仍是 `94` —— 值在首帧之前就已就位，界面上不会跳变。
   要断言尺寸，请用 `Qt.callLater` 推迟一轮。

3. **注释首行不要以 `qmllint` 开头。**
   `/* qmllint 如何如何 */` 会被当成指令本身来解析，
   报出一串 *directive on unknown category*。把「qmllint」挪到句子中间即可。

4. **想看 QML 的真实报错，必须设 `QT_FORCE_STDERR_LOGGING=1`。**
   第 1 条说 `console.log` 看不到 —— 但**引擎自己的报错**同样看不到：
   Qt 在 Windows 上把 `qWarning` 送进 `OutputDebugString`（调试器通道），
   不是 stderr。于是组件加载失败时，日志里只剩 qml 工具自己补的一句
   `Did not load any objects, exiting.`，**既不说哪个文件、哪一行，也不说
   哪个属性**，排查只能靠二分猜（M13 实录：为此写了 9 个探针文件，
   而真相只是"探针忘了 `import QtQuick.Layouts`"）。

   ```bash
   QT_FORCE_STDERR_LOGGING=1 ./tools/run.sh HelloM13
   ```

   加上之后，同一处失败立刻变成一行可定位的报错：

   ```
   probe_c5.qml:5:19: Non-existent attached object
   ```

   这个变量已经**内置进 `tools/{run,test,shot}.sh`**（可用同名环境变量
   覆盖为 `0`）。`test.sh` 还会在某个测试文件失败时把这段 stderr 一并打印
   —— 否则"组件根本没加载起来"会表现成"8 条断言全错"，看着像逻辑全崩。

5. **用 `eval` 拼 `find` 的参数列表，`*` 会被二次展开。**
   `tools/clean-cache.sh` 原先是
   `PATTERNS='-name "*.log" ...'; eval "find .cache \( $PATTERNS \) ..."`。
   赋值时的引号只挡了第一层 —— **eval 里还有一层 shell 展开**，
   裸的 `*.log` 按**当前工作目录**被展开成实际文件名（实测变成了
   `aqtinstall.log`，因为那是仓库根目录下唯一匹配的文件），于是
   `-name '*.log'` 变成 `-name aqtinstall.log`，在 `.cache` 里永远匹配不到
   任何东西。这个 bug 长期隐形：旁边的 `*.out` 恰好没匹配到文件，
   才侥幸还能用（`*.php` 式的"碰巧正确"）。

   正解是**数组 + 直接调用**，把 glob 交给 `find` 而不是 shell：

   ```bash
   PATTERNS=( -name '*.log' -o -name '_*.qml' )
   find .cache -maxdepth 1 \( "${PATTERNS[@]}" \) -type f -delete
   ```

   同类教训还有一次：模式里写 `-name 'shot_*.qml'` 会把**要保留**的抓图入口一起删掉。**清理规则必须用显式清单 + 反例验证**，
   不能靠通配符的"看起来对"。

6. **变异测试有两条"假绿"通道，两条都会让你得出相反结论。**
   变异测试是"故意改坏一处实现，看断言有没有红"。它的结论天然是**反向**的
   —— 红了能证明断言有效，绿了只能说明"这次运行里那处改动生效了**且**断言
   恰好没覆盖"，而"生效了"这个前提经常不成立。

   **通道一：改了 `src/`，跑的是 `.cache/qmlimports` 里的副本。**
   `qml -I .cache/qmlimports` 读的是那个**拷贝**，`lint.sh` / `test.sh` /
   `shot.sh` 每次运行开头才重建它。只改 `src/` 不重建，新代码根本没进这次
   运行 —— 打印出来是一串漂亮的"✓ 已被断言抓住"（因为没有断言失败）。
   修法：变异后**先重建 import 树，再用 md5 比对证明"确实换了输入"**
   （M17 实录：`98be…` vs `90f8…`，确认前后是两份文件）。
   这和 M16.1 那条「A/B 对照必须先证明 B 是新产的」是同一条，换了个马甲。

   **通道二：Python `subprocess` 里的 `"timeout"` 会解析到 Windows 自带的
   `timeout.exe`。** 那个程序是"等待 N 秒"的意思，收到 `["timeout", "60", …]`
   会报无效语法并**立刻退 1**。于是 `"timeout 60 qml …"` 这一路的批量变异
   全部"退出码 1"，脚本把它读成"断言抓住了"，三行结论全是假的。
   修法：别自己拼 `timeout`，用 `subprocess.run(cmd, timeout=120)`。

   **通道三：只重建了 `Contracts`，而变异目标在别处**（M18.1 新增）。
   变异令牌文件（`src/foundation/tokens/*.js` 或 `src/themes/*/tokens.js`）时，
   只重铺 `Contracts` 是没用的 —— `qmlimports` 里的 Foundation / 四套主题还是
   旧副本，"令牌改坏了"和"没改"于是给出**同一个退出码**。修法：变异哪一层就
   重建哪一层（令牌侧变异脚本 现在同时重铺 Foundation 与四主题）。
   **"重建 import 树"不是一个动作，是一组动作 —— 漏掉谁，那个谁就是假绿。**

   三条通道的共同点：**失败的样子是"成功"**。变异测试的脚本必须先证明
   "这次运行和上一次不是同一个输入"，否则它在验证的是它自己。

7. **一个仪表在没接上信号的时候指向"正常"，比指向"异常"危险得多。**
   这是第 6 条的同族，但发生在**核验器自己**身上，所以单列一条。

   截图核验脚本读的文件名是 `m17_<主题>_<light|dark>_<场景>.png`，
   正则解析出场景来查期望表。一开始，不匹配的文件名只是 `continue` —— 而
   "跳过的文件"不进失败计数。于是把它指向一张**叫别的名字**的图，它的输出是：

   ```
   ---- 0 张通过，0 张有问题
   ```

   退出码 **0**。一张都没量，却说"全部通过"。

   发现它的是渲染侧变异测试：改了 `y: 0`（就是 M17 那个真 bug），图都肉眼可
   辨地变了（`ImageChops` 差出一大片），核验器却给了绿。当时第一反应是
   "判据太松"，真实原因是**它根本没读那张图**。

   修法两条：① 文件名不匹配 = **失败**，不静默跳过；② "一张都没量到"一律
   退出 1。

   推广开来：**任何一个门禁都要能回答"我这次到底检查了什么"**。检查数为 0
   必须是失败，而不是成功 —— 因为 0 的成因通常是"路径写错了 / 文件没生成 /
   上游步骤被跳过"，而这些恰恰是门禁最该叫出来的情况。
   同族的还有 `find` 返回空时 `for` 循环体一次都不执行、
   `grep` 没匹配到就返回 1 被 `||` 吃掉 —— 都是"没信号"伪装成"没问题"。

   M19 又添一个同族的：**没有配变异脚本的门禁，等于一道"看起来在守"的门禁。**
   `smoke_m19_theme.qml` 先写好了，但它的变异脚本是收口时才补的 —— 在那之前，
   那 8 条断言的"全绿"和"空转"在输出上长得一模一样。规矩是：
   **每加一道新门禁，就在同一个回合里给它一枪**，
   否则你并不知道自己加的是门禁还是装饰。

   M20 在这条上又补了三笔，都是"**判据自己也会错**"：

   - **判据必须落在"会坏的那一边"。**`QSkinTextarea` 的截断缺陷（直写
     `editor.text` 打掉那条绑定）只读 `charCount` 是**看不见**的 —— 宿主写的
     就是 `text`，`charCount` 也跟着变，不一致的那一边在**编辑器**里。
     为此给 `QSkinTextarea` 新公开只读属性 `editorText`，与 `QSkinRate.fracAt()`
     同一手法：**把属性侧与像素侧要量的那个数公开出来，让两边指的是同一个东西**。
   - **测量的时序要钉死，别让绿依赖"刚好被求值一次"。**`text` 与 `editor` 之间的
     回推**不是同步的**：在 `taMax.text = "abcdefgh"` 之后**立刻**读 `charCount`
     期望 4，它曾经是绿的 —— 只要多挂一条无关绑定就由绿转红（M20 补上
     `editorText` 的那一刻它就红了）。正解是把初值放到**声明期**（截断发生在
     创建时）、判定放到 `run()`（`Qt.callLater`，至少过了一轮）。
   - **主动扩一档输入维度，往往比多写几条断言更值。**M20 的像素门禁原先只看
     亮色；收口时补了一张 `mode=dark` 的实拍，**当场打出一个判据缺陷**
     （见第十节最后一条：比例门槛被页底色抬高，同一颗圆点亮 7.83 / 暗 9.45）。
     补图之后还给那张暗色图单独配了一枪"只改暗色令牌"的变异 —— 否则它只是
     装饰性的存在，没有任何东西证明它真的参与了核验。

   还有一条不属于"门禁"但同族：**一条红断言里可以同时藏着实现错与判据错**。
   M20 的 `smoke_m20.qml` 从三条红修到全绿，其中三处是真源码缺陷（组序 /
   markerSize / 惰性绑定），两处是**断言自己写错了**（OTP 总宽多算一道缝
   312 vs 实测 304；`lbMuted` 那条恒假）。**先分清是哪一种再动手** ——
   判据错的时候改实现，只会把对的改坏。

8. **本环境有「安全删除守卫」，而项目自己的清理工具没跟它对齐 ——
   被拦下的样子是"脚本自己退出了"。**

   宿主会拦 `rm`：**一条命令里累计删除的文件数**达到阈值（守卫代码里
   默认 20，本机实测配成 50）就要求人在宿主弹窗里确认；未确认时 `rm`
   直接非零退出，stderr 打一行

   ```
   [safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":91,"threshold":50,"scope":"turn",...}
   ```

   而 `.cache` 里**一份 `qmlimports.stale.*` 就有近百个文件** —— 必然触发。
   配套地，`lint.sh` / `test.sh` / `shot.sh` 之所以用 `mv` 而不是 `rm` 来
   换掉旧 import 树（M9.x 的原始动机），就是这个守卫。

   `clean-cache.sh` 早期版本带 `set -euo pipefail`，**第一个被拦下的 `rm`
   就把整个脚本打死**。人看到的现象是"跑了一下就没了"，如果再套一层
   `| tail -N`，连那行 marker 都被吞掉 —— 于是它和"脚本有 bug""机器太慢"
   完全无法区分。M17 收口时为这一件事白卡两轮，第二轮才想到去看被 `tail`
   吃掉的 stderr。

   两条结论：

   ① **清理类脚本必须容忍单次删除失败**，并汇报"清掉多少 / 还剩多少"，
      而不是 `set -e` 一死了之。
   ② **跑清理要在前台**。守卫的确认是按"这一次工具调用"记的，人确认一次
      就能放行同一命令里后续所有删除 —— 但前提是弹窗递得出去。塞后台跑
      = 没人能点确认 = 必然全被拦。

   实测：前台跑一次，**221 份陈旧 import 树全部清掉、0 份被拦**，
   `.cache` 从 200M / 330+ 项降到 3.3M / 13 项。耗时 **27 分钟** ——
   守卫对**每一个**目录都要递归数一遍文件，这个开销是真实的，
   别把它当成卡死然后手动掐掉。

   这条分支本身也是**被证伪过**的，不是印刷品：造一个 51 文件的
   `qmlimports.stale.guardprobe`（51 ≥ 阈值 50），**后台**跑一次 ——
   守卫拦下，脚本输出「1 份 → 清掉 0 份，剩 1 份」+ 处置说明，并且
   **`exit=0`**（旧版会正好在这里被 `set -e` 打死）。

   顺带两个否证，省得下一个人再试：
   - **只读文件挡不住 `rm -r`**（`chmod 444` 之后实测 `rm exit=0`）。
     想造"删不掉"的目标，得靠守卫本身，别指望权限位。
   - **用 PATH 前置一个假 `rm` 替身没用** —— 环境会把 shim 目录重新抢到
     PATH 前面，所以"替换命令"这类测法在这里不成立。

   M21 又往前推了四步：

   - **Python 的 `shutil.rmtree` 一样被拦**（不只是 `rm`）。所以"绕开 shell
     改用 Python 删"不是出路。属性侧变异脚本 的 `rebuild()` 里那个 `rmtree`
     就是这么**在后台被杀的** —— 进程退出码 1、日志只剩一行守卫 marker，
     看上去像"脚本逻辑写错了"。当时写了个一次性探针对照才看清：
     **同样的 60 个文件，前台跑 `rmtree 成功`，后台跑被拦。**
     （那个探针按清理策略已被清除；结论就是上面这半句，不必再复现。）
   - **根治办法是让脚本根本不需要删。** 把 `rmtree(dst)` + `copytree(src, dst)`
     换成 `copytree(src, dst, dirs_exist_ok=True)` —— **只写不删**。
     M21 顺手把这八道变异脚本一起改成这个写法，
     "跑一半被杀"再没出现过，而且更快（覆盖只写真正变了的那部分）。
     ⚠️ **改令牌文件时不能省**（令牌侧变异脚本 / 令牌侧变异脚本（另一道） /
     令牌侧变异脚本（第三道） 这类要同时重铺 `Contracts` + `Foundation` + 四主题），
     只覆盖一层会得到"改坏了 == 没改"的同一个退出码。
     （属性侧变异脚本 里原先还留着一句**错的推断**——"Python 直连文件系统
     不经过 guarded delete"—— 本轮一并纠正了。）
   - **只清"可重建的构建产物"时，Python 直接删比 `clean-cache.sh` 快得多。**
     守卫那 27 分钟的开销来自"对每个目录递归数一遍文件"。而这批
     `qmlimports.stale.*` 全是下一次 `lint.sh` / `shot.sh` 会重建的东西，
     一次 `shutil.rmtree` 清掉 73 份只要 **16 秒**（`.cache` 112M → 12M）。
     **前提仍然是前台跑**，而且要能自己回答"删掉的确实是产物"。
   - **"没打算删"的地方也会删：`shutil.move(src, dst)` 在 `dst` 已存在时
     退化成 `copy2` + `os.unlink(src)`，那个 `unlink` 就是一次删除。**
     渲染侧变异脚本 的复原逻辑原本是
     `shutil.copyfile(p, p + ".mutbak")` … `finally: shutil.move(p + ".mutbak", p)`，
     看着只是"把备份搬回来"，实测**在后台被守卫杀死在第一组之后**，日志只剩
     一行 `抓住 A/外扩量被丢掉` 加一串
     `"targets":["...\\src\\contracts\\QSkinPopover.qml.mutbak"]`。
     更坏的是它**留下了 `.mutbak` 残骸而循环本该继续** —— 现象与"脚本逻辑写错"
     完全无法区分。（另三道 `_px.py` 用 `copy2` 覆盖，所以一直没事。）
     修法与 ② 同源：**备份放内存、原地 `write()` 写回，全程不出现删除动作**；
     并加一条自检"写回后盘上内容必须与原文逐字节相等" —— 上一版恰恰是
     **复原这一步**被杀的，而循环并不知道，还在往下跑。

   和第 5 条是同一族：**工具的"失败"和"没有输出"长得一模一样。**
   判断依据必须是"它报告自己做了多少事"，而不是"它跑完了"。

9. **命令式方法调用不产生属性依赖 —— 它骗得过所有属性断言。**

   ```qml
   readonly property point targetOrigin: target.mapToItem(null, 0, 0)
   ```

   `mapToItem()` 是**方法调用**，不是属性读取。QML 的依赖追踪看不到它，
   于是这个绑定**只求值一次**：锚点一移动，浮层留在原地。
   而属性侧读 `targetOrigin` **永远是对的**（它确实是"当时那个真值"），
   所以"断言全绿、界面全错" —— 本项目第 6 次撞上这个形状。

   修法是把依赖**显式列出来**：

   ```qml
   function _anchorDeps() { return [target, target.x, target.y,
                                    target.width, target.height, target.parent] }
   readonly property point targetOrigin: (_anchorDeps(), target.mapToItem(null, 0, 0))
   ```

   同族还有一条更早的（M20，见第三节）：**派生量要抽成纯函数**，
   别做成"调用一次拿一个值"。判断标准很简单 ——
   **问自己"我改了哪一个属性会让它重算"，答不上来就说明它没有依赖。**

   推论一条，用在测试上：**定位断言的两边不能用同一个常量。**
   `smoke_m21*.qml` 一度把锚点坐标写成字面量，于是
   "面板顶边 = 锚点底边 + gap"两边是同一个数 —— 这条断言永远绿。
   真正要量的是"经过 `mapToItem` 换算之后"的那个数。

10. **变异脚本的替换文本，要对**目标语言**的语法负责 ——
    否则"目标没跑起来"会和"判据报红"同码。**

    门禁侧变异的 `B1` 首轮报 **MISSED**：退出码 1（看上去"红了"），
    但预期的那条文案没出现。拆开发现是**变异脚本自己**写错了替换文本：
    里面用了 C 风格的 `/* 变异：退回硬编码 */`，而目标是 **Python** ——
    `/* */` 在 QML/JS 里是注释、在 Python 里是**语法错**。核验器当场
    `SyntaxError`（`invalid character '：' (U+FF1A)`），而 Python 的语法错
    退出码**恰好也是 1**，与"核验器报了一条 FAIL"同码。
    这一枪测的其实是"文件能不能跑"，**从头到尾没碰到它声称要测的那件事**。

    两道处置（都建议照做）：

    - **干跑阶段机械检查一次**：对 `.py` 目标把替换后的全文 `compile()`
      一遍。`.cache/_preflight_m21.py` 现在同时检查"目标串恰好出现一次"
      与"替换后仍能解析"。补完之后**先把老 bug 灌回去验证它会红** ——
      它精准报出了第 124 行与老替换文本。
    - **运行器把"目标没跑起来"单列成 `BROKEN`**，与 `MISSED` 分开报：
      `BROKEN` 要改的是**变异脚本**，`MISSED` 才要改**判据** ——
      指向相反，混在一起报几乎必然修错地方。
      （判据正常跑起来时 stdout 必有它的运行头，用它当信号。）

    这是第 6 条"假绿通道"的第三个成员，而且是最毒的一个：
    前两个是"没查"和"查了个假的"，这一个是**"查的东西根本不存在"**。

11. **重写源文件的脚本必须显式 `newline=""` —— 本仓的换行符是混的，
    Windows 上的默认写路径会把整篇 LF 转成 CRLF。**

    实测本仓现状：`src/` 下 126 个 `.qml` 里 **13 个 CRLF / 113 个 LF**
    （CRLF 那 13 个：`QSkinInputOTP` / `QSkinLabel` / `QSkinPagination` /
    `QSkinPopover` / `QSkinRadioGroup` / `QSkinRate` / `QSkinSelect` /
    `QSkinTextarea` / `QSkinToggleGroup` / `Slots` / `TimeCell` /
    `ButtonBar` / `Shadcn`）。而且本仓**既不是 git 仓库、也没有
    `.gitattributes`** —— 没有任何东西在负责统一它。

    `newline=None`（`open()` 的默认值）下，**读**会把 CRLF 归一成 LF，
    **写**会把每个 `\n` 翻成 `os.linesep`（Windows = `\r\n`）。两者一起用，
    "读进来原样写回"看着是恒等的 —— **但那只在目标本来就是 CRLF 时成立**。
    拿 `QSkinMenu.qml`（纯 LF）实测：

    ```
    原文                11458 字节, CRLF=0
    默认 newline 读→写   11763 字节, CRLF=305   ← 305 行全部被重编码
    newline="" 读→写     11458 字节, CRLF=0     ← 字节全等
    ```

    最阴的地方是**它骗得过所有断言**：Python 读回来时又把 CRLF 归一了，
    所以文本比对仍然相等，`old in src`、`==`、Lint、冒烟测试**一个都不会红**。
    唯一能看见它的方式是**比字节**（或者比 `git diff` 的行数 —— 本仓没有 git）。

    这条不是新规矩，是**本项目的既定写法漏了一道**：M17 起每一道变异脚本
    （十三道变异脚本）都已经带着 `newline=""`。
    漏掉的是 渲染侧变异脚本 —— 它的主循环当初直接写了内联的裸
    `open(path, "w", encoding="utf-8")`，**绕过了同文件里已有的 `read()` /
    `write()` 辅助函数**（它的兄弟 渲染侧变异脚本（另一道） 就是老老实实调
    这两个函数的）。修法只有一句：主循环改调 `read()` / `write()`。

    推论，给下一个人：**同一目录下的兄弟脚本是最便宜的对照物。**
    这次的真凶不是"换行符很微妙"，而是"我写了第 14 个脚本，却没抄第 13 个"。

12. **变异脚本被硬杀时 `finally` 不执行 —— 源码会一直带着「改坏的那一份」，
    而门禁是有时间窗口的。**

    这是本轮最贵的一条，因为它**不是"某条判据写弱了"，是"源码本身脏了"**。

    实测：`src/contracts/QSkinLabel.qml` 的

    ```
    visible: root.required        →        visible: true
    ```

    在源码里躺了两个多小时。它是 渲染侧变异脚本（另一道） 的一次运行在**第 [E] 枪
    落刀之后、复原之前**被硬杀留下的（`finally` 拦得住异常，拦不住
    SIGKILL / 安全删除守卫 / 外层超时）。症状是本项目最熟悉的那个形状 ——
    **`required` 属性读出来完全正确，而屏幕上每个标签都带着一颗红星。**
    这正是第 6 条"属性对、界面全错"的第 7 次。

    为什么没人发现，值得逐条看：

    | 环节 | 当时的状态 |
    |---|---|
    | `lint.sh` | **看不见** —— `visible: true` 是完全合法的 QML |
    | `smoke_m20.qml [4]` | **看得见**（那条与字体无关的差式立刻红） |
    | 上一次跑 `test.sh` | **17:13**（全绿） |
    | 变异落刀 | **17:14–17:16** |
    | 下一次跑 `test.sh` | 直到本轮收口才跑 —— 中间没有任何东西再看过一眼 |

    也就是说：**"跑过门禁"这句话有一个时间窗口，而变异恰好发生在窗口之后。**
    处置不能是"以后记得再跑一次"（记不住的），得**直接问源码要答案**：

    > `./tools/check-mutation-residue.sh` —— 把 15 道变异脚本里的
    > `(文件, 原文, 改坏成)` 全部抽出来（现为 **128 条 / 触及 53 个文件**），
    > 逐条判定源码里现在装的是**原文**还是**改坏成**。

    它的三个设计要点全是被实测打出来的：

    - **不能用 `exec` 加载变异脚本。** `_preflight_m21.py` 靠
      `src.split("def find_qml()")[0]` 截断主体 —— 那对 某一批的变异脚本 /
      `*_theme.py` 有效。但 `*_px` 这类
      **没有 `find_qml()`**，而 渲染侧变异脚本（另一道） **连
      `if __name__ == "__main__"` 守卫都没有**（主体直接写在模块级）。
      对它们 exec 一次 = **真的又跑一轮变异**。
      → 改用 `ast` + 一个小求值器（只认常量 / 名字 / 元组 / 列表 / 字典 /
      字符串拼接 / f-string），**不执行任何代码**。
    - **三种书写形状都要认，少认一种那批变异就静默不在审计范围内。**
      实测出现过：① `edits=[(路径, 原, 改)]`；② `dict(path=…, old=…, new=…)`
      ——**注意它是 `ast.Call`，不是 `ast.Dict`**（后者只是 `{…}` 字面量），
      第一版就栽在这里，7 道脚本一条都没抽出来；③ `edits=[(SMOKE,) + INJECT]`
      这种**拼接**出来的三元组。另外路径**不固定在首位**（渲染侧变异脚本
      是六元组 `(标签, 路径, 原, 改, 期望, 说明)`，路径在索引 1）。
      → "抽不到"必须**报成失败**，不能当成"没东西可查"。
    - **分类规则要按包含关系分型**，"先看原文"和"先看改坏成"**都不对**：

      | 关系 | 例子 | 只能先看谁 |
      |---|---|---|
      | 改坏成 ⊂ 原文 | OTP：`return i*stride + seps*sepStride` → `return i*stride` | 原文（改坏成是它的前缀，原文在位时它也在位） |
      | 原文 ⊂ 改坏成 | RadioGroup：往两句之间插一句 `root._sync()` | 改坏成（原文在位说明不了任何事） |
      | 互不包含 | QSkinLabel：`visible: root.required` → `visible: true` | 原文（落刀前核对过"原文恰好一次"，所以原文还在 = 替换没发生） |

      两版判据各自栽过一次，**都是假阳性**：第一版"先看改坏成"，把**健康**的
      `QSkinTextarea` / `QSkinInputOTP` 报成残留；第二版把 `QSkinAvatar` 报成残留，
      因为那条变异的改坏成**只有三个字符** `: 0`，而任何 `foo: 0` 都含它。
      **审计器报假阳性的代价是下一次没人信它** —— 所以宁可把规则写细。

    **审计器自己也要被证伪**：把三类残留分别灌回源码 → **3/3 认出**
    （退出码 1、点名到具体文件），每次灌完都逐字节复原。

    一句话收口：**门禁守的是「实现会不会错」，审计器守的是「源码是不是干净的」，
    这两件事不能互相替代。** 变异测试越是好用，越需要有东西盯着它自己有没有收干净。

13. **Layout 的子项只能用 `Layout.*` 表达尺寸 —— 这条已经付了三次代价。**

    `width:` / `height:` 在 Layout 里是**愿望**，Layout 会用 `implicitWidth` /
    `implicitHeight` 覆盖它。三次的实际后果各不相同，一次比一次隐蔽：

    | 处 | 写法 | 后果 | 谁抓到的 |
    |---|---|---|---|
    | `QSkinDialog` footer | `ButtonBar` 缺 `fill: true` | 按钮停在**左**内边距（`align: "end"` 没有可推的空间） | M22.1 的侦察诊断屏（躺了 14 个里程碑） |
    | 抓图入口的结果列 | `width: win.resW` | 实际按 `implicitWidth = 420` 摆，右沿超出窗口 20px；内容居中，**肉眼看不出来** | 像素核验的读数 |
    | `QSkinResult` 状态码 | `height: root.glyphSize` | 实际 48 而不是 64；404 ↔ success 整页差 16px | M22.2 的干净探针实验 |

    遇到"我明明给了宽高却不起作用"，先查这一条。
    尺寸一律走 `Layout.preferredWidth/Height`（或 `fillWidth/fillHeight`）。

14. **`Popup` 不是 `Item`：它的内容要从窗口树上认领，而且只在打开期间存在。**

    三条都是实测出来的：

    - **摸不到里面的控件。** `findChild` 找不到 `Popup` 里的东西，得从
      `root.Window.window.contentItem` 认领，再靠 `underNode(o, root)` 摘出
      **本文件的**那一份（同一屏上可能有多个实例，不筛就串台）。
    - **断言必须在打开之后跑。** `Popup` 的内容对象在关着的时候**不存在**，
      打开前取到的是 `null` —— 而那个现象看起来和"属性名写错了"一模一样。
    - **抓图要抓 `win.contentItem`，不能抓自己铺底的 Rectangle。** 未设 parent
      的 `Popup` 被 Qt 挂到 `Overlay.overlay` 上，而 overlay 是画布的**兄弟** ——
      抓画布等于把对话框整块丢掉，而图看起来"什么都没坏"。
    - **静态遍历要认 `data`，断言要等动画。** `Popup` 只在 `data` 里（`children`
      里没有），而**进场动画未收尾时 `mapToItem` 会把缩放算进去**（`QSkinDialog`
      的 `scale 0.96 → 1`，量到的间距就是 0.96 倍的，看着"差不多"）。两处都是
      M22.1 那支探针的第 1 版用"前三条断言全红（退出码 135）"换来的。

15. **`_` 前缀属性跨文件是只读的，而引擎的报错在误导你。**

    从测试文件写 `ad._confirmIntent = true`，得到的是
    `Cannot assign to non-existent property "_confirmIntent"` ——
    **"不存在"三个字是假的**：它存在，只是不可写。读一直是正常的。

    推论：想给一条内部不变量造状态，先确认它**从外部可达**；不可达就如实记成
    "当前不可证伪"，而不是把断言删掉了事（M22 那条上升沿归位就是这一档 ——
    它的唯一置位入口紧接着 `close()`，状态本就不可达）。

16. **文本形状的判断交给解析器，不要用计数。**

    两个实例，同一个教训：

    - 查"字符串被内层引号截断"时，我用的是"这一行引号数是不是奇数" ——
      它**漏掉了**真正断掉的那一行（`"…"关掉即取消"那条路"` 恰好 4 个引号，
      偶数）。**判据要与被测量的形状匹配**：语法问题交给解析器说话
      （QML 交给 qmllint，Python 交给 `ast.parse`）。
    - 查锚点命中数时，`read().count(old)` 会因为**行尾不同**数出 0 ——
      本仓两套行尾混着，必须按**各文件自己的行尾**归一之后再数。

    这是**第二次**犯同一个错（令牌侧变异脚本（第三道） 那次已经记过一次：
    "判定权交给 `ast.parse`，不是引号奇偶"）。所以它值得单列一条，而不是
    附在别的条目后面。


### 十一·附：Qt 行为陷阱速查

> 上面十六条讲的是**构建 / 测试工装**的坑，这一组讲的是 **Qt 本身的行为**。
> 它们是**排期文档**之外反复用到的一层常识，M31 第二件时从工作记忆迁到这里
> （工作记忆有体积上限，而这里才是"坑大全"该住的地方）。
> 每条后面括号里的批次是**第一次撞到它**的那一批。

**尺寸**

- **Layout 子项的尺寸只能用 `Layout.*` 表达**，写 `width/height` 是"愿望"（读回来
  是布局算出来的值，不是你写的值）。更要紧的是：**Qt Quick Layouts 只在"子项
  implicit 尺寸变化"时重跑**，而它读尺寸那一次可能发生在**字体就绪之前** ——
  于是布局**永不重跑**。症状是本项目最熟悉的那个形状：**几枚声明不同的东西
  画成了一样宽**，而属性侧与冒烟全绿。→ **自定义委托项一律显式写
  `implicitWidth/Height`。**
- **`Shape` 的隐式尺寸由它自己按路径包围盒算**，你写的 `implicitWidth:` 绑定会被
  静默盖掉 → 要控制它在 Layout 里的尺寸，用 `Layout.preferred*`。

**坐标**

- **子项的 `x`/`y` 是相对内层 layout 的局部坐标** → 读落点一律 `mapToItem(容器)`。
  注意**命令式方法调用不产生属性依赖**（`mapToItem()` 只求值一次），判定法是问
  "**改哪个属性会让它重算**"，答不上来就是没依赖。
- **布局余量的分配形状，两种容器不一样，别互相推。** 主轴默认 `flex-start`（M29
  起），`justify` 只有 `start`/`center`/`end`（`between`/`around` 经八档实测否决）。
  实测读数在 `COVERAGE.md` 的 1.1，那里是唯一出处。

**像素 / 出图**

- **`grabToImage` 按 devicePixelRatio 出图**（本机 1.5×，900 逻辑宽 → 1350 物理宽）
  → 扫行的 `y` 要折算。**前景色与背景色要"一图一标定"**（取全图众数），不要写常量。
- **8 位令牌色是 QML 的 `#AARRGGBB`，不是 CSS 的 `#RRGGBBAA`** → 比色前必须先
  `flat(token, 底色)` 合成。
- **抓图载体三选一**（M31 踩了三次，三种各中一次）：
  1. 抓**本 Item** —— 挂在 `Overlay` 上的东西（`Popup`）**不在里面**，图里没有它；
  2. 抓 **`win.Window.window.contentItem`** —— 它是 C++ 的 `QQuickRootItem`，
     `grabToImage` 直接报 **`item has no QML engine`**（实测）；
  3. 抓 **`popup.contentItem`** ✔ —— 它是 QML 声明出来的 Item，面板本体就在里面。
- **自证行必须移出被抓的 `canvas`。** 把带文字的"自证行"抓进图里会引入**栅格化
  抖动**：实测两例分别 29 像素（差 42）与 137 像素（差 1），全部落在文字外接框内。
  移出之后两次运行 **0 差异**。

**跑场景**

- **`qml` 把 `k=v` 当成"第二个要加载的文件"，而且加载失败仍返回 0。**
  → 夹具**不要靠命令行参数分档**（"参数没生效"与"这一档没问题"长得一模一样）；
  要分档就**无条件全实例化，用行号归因**。
- 像素场景**不要 `import` 主题**、`.sh` **不要传 `theme=`**；`QSkinWindow` 没有
  `themeName`，切换主题走 `Theme.install()/reset()`。
- **`-platform offscreen` 把指针停在 (0,0)** → 夹具不要摆在原点。

**时序 / 响应式**

- **`Behavior on color` 会让"切主题后立即读颜色"拿到动画起点。** → 读颜色等
  `Theme.motion.fast + 80`，**读几何不用等**。
- **`property var` 就地改写不触发通知**（`arr.push(x)` 不会让绑定重算）。
- **`Qt.exit()` 会打断剩余的 `Component.onCompleted`。** → 夹具里 `onCompleted`
  **只读不退出**，退出挪进 `Timer`。否则各档读回的都是默认值，只有"无条件实例化
  且排在 `onCompleted` 最前"的那一档生效 —— 而它看起来**像是**其余档都"没问题"。
- **`Component.onCompleted` 的触发顺序是逆声明序**（兄弟节点之间），子项比宿主晚跑
  → 按下标路径排序，不要按声明顺序假设。

**导入**

- **四角独立半径（`topLeftRadius` 等）在版本化导入下不存在** → 必须
  `import QtQuick`（**不带版本号**）。
- **`Layout.*` 附加属性需要 `import QtQuick.Layouts`** —— **源码与探针都要。**
  探针少了这一行，`o.Layout.alignment` 在 JS 里是 `undefined`，而 `fmt()` 会
  **静默一个字都不打**：**"没输出"与"没问题"长得一样**。本仓统一写
  `import QtQuick.Layouts 1.15`。
- **往单例注入语法错 ≠ 加载失败**（Qt 惰性编译，只在第一次引用时才抛）。

**成组协议**

- **`QSkinRow` 不能当组容器** —— 它的 `default property alias data` 会把子项挂到
  **内层真 Row** 上，于是"组"的写法**静默失效**。组容器要 `import QtQuick 2.15 as QQ`
  + `QQ.Row`。
- 协议是**拉模型**：成员声明 `isGroupMember` + `groupPosition`（自己读 `parent`），
  组声明 `isInputGroup` + `positionOf(item)`；方位由 `CornerUtil.positionOf(idx, n)`
  现算（`n ≤ 1` → `standalone`）。

**假读数（能骗过所有断言的那一类）**

- **锚点必须覆盖完整语法单位。** 跨行三元只截半行 → **语法错** → 整个模块编译
  失败 → 退出码 **2**，看起来**恰好**像"第 2 条断言失败"（255 之外的假位掩码）
  → 跨行就把 `\n` 写进锚点，并**两路取面对账**。
- **半角引号会截断 Python 字符串字面量** → `SyntaxError`，且**报错行指向上一句末尾**。
  变异脚本的 `why` 里一律用全角「」。
- **赋值失败后 QML 保留上一次的值，不是归零。**（M31 实测）`QSkinNavigationMenu` 的
  假宿主漏报 `width`，赋值失败后保留下来的正是 `popup.width` 的默认 320 —— 于是
  画面上完全看不出来，只在累积日志里堆了 658 行。**"只有警告没有异常"的现象，
  多半能在这一条上找到解释。**
- **`PropertyChanges` 不写目标就落不到目标上**（M31 第二件实测）：
  `PropertyChanges { opacity: 0 }` 会把 `opacity` 当成 **`PropertyChanges` 自身的
  属性**去赋值 → 运行期 `Cannot assign to non-existent property "opacity"`。
  两种可用写法：

  ```qml
  PropertyChanges { target: t; opacity: 0 }   // 运行期对，但 qmllint 报
                                              // Quick.property-changes-parsed（lint 会红）
  PropertyChanges { t.opacity: 0 }            // 两边都过 ✔（本仓采用）
  ```

  ⚠ 与上一条叠加时后果最坏：赋值失败 → 保留旧值 → **画面正常、只有日志在堆**。
  `QSkinToast` 的淡出就是这样**从来没工作过**（M31 判决并修）。

**渲染侧不可观测（判据要换个落点）**

- **`Text.maximumLineCount <= 0` ≡ 「不限」** —— 渲染结果与不写它**逐字相同**，
  属性回读也原样保留 → 这类判据只能落在**属性回读**上，别指望像素。
- **字体：`Inter` 与 `JetBrains Mono` 逐位量完全相同 → 本机没装 mono →
  "给这段加 mono"是个空操作。** 不要用字体名做判据。
### 十一·附二：契约层的实现不变量（改 `src/` 前必读）

> 这一节从 `README.md` 第十节搬来（2026-09-16）。讲的是**改 `src/` 才会碰到**的
> 实现机制 —— 使用者在页面里撞不到，所以不该占说明书的篇幅，但丢掉可惜。
> 括号里的批次同上一节：**第一次撞到它**的那一批。

**表格 · 列宽与固定列**

- **「等分列不可拖」靠回查宽度来源实现**（M12）。不要写成
  `colLayout.widths[i] > 0` —— 等分分支会给每个自动列都填上 `share`，该判断恒真，
  规则等于不存在。正解是 `_hasExplicitWidth()`。
- **量宽探针的字重不能经过中间属性**（M12）。`font.weight` 要直接依赖 `isHeader`，
  绕一层 `readonly property` 会形成循环依赖；QML 遇到环不报错，只静默标记该链不可靠。
- **钉住列在「内容侧」和「屏幕侧」是两个宽度**（M16）。`_fixedWidth` / `_rightTotal`
  回答"哪几列不参与滚动"，`_leftWidth` / `_rightWidth` / `_middleWidth` 回答"三个区
  各占多宽"。容器不比钉住列窄时两者相等，窄了就分叉 —— 这时必须用屏幕侧那组去摆区，
  否则右固定区会算出负的 `x`，横着压到左区上面。
- **`_maxScrollX` 化简掉左右固定宽之后 = 内容总宽 − 容器宽**（M16）。给表格加固定列
  **不会**改变滚动范围 —— 这条同时是"中间区与右固定区在滚到底时恰好接上"的代数形式。
- **左右两道渐隐条是两个独立条件**（M16）：左条在 `contentX > 0` 时出现，右条在
  `contentX < _maxScrollX` 时出现。不是"同一条画两遍"。
- **固定区不做第二个 `Flickable`**（M13）。两个 Flickable 互相绑 `contentY` 会来回
  打架，拖动时高频抖动。固定区只做表体的只读投影（`y: -body.contentY`），代价是
  滚轮落不到它头上，要用 `WheelHandler` 手动转发。
- **两区不重叠，所以不给固定区画底色**（M13）。叠层式固定列要额外让底色跟着行
  hover / 选中一起变，一处没对上就是"钉住的那列悬停时不变色"。

**树 · 展平 / 勾选 / 排序**

- **树形的勾选列一律不渲染**（M14）。`selectedIndexes` 是 `rows` 的**下标**，而折叠
  分支里的节点压根不在 `rows` 里 —— 那个下标指向的是别的行，语义上是错的。判据只有
  `_showCheckColumn`（`checkable && !treeMode`），所有取值点（固定区宽、内容总宽、
  列宽下限、`colLayout` 前置宽度、表头全选、数据行 checkbox）都必须指向它。
- **展平层绝对不能读 `page`**（M14 实测）。`pageCount` 依赖展平结果、又反向写 `page`，
  展平里一旦读 `page` 就成环。QML 报一次 `Binding loop detected` 之后会把该绑定标记为
  不可靠，**数值冻在某一轮且永不恢复**。正解是从结构上断环（`_visibleRows` → `_view`
  → 只读出口），不是加守卫压住。
- **「两套视图」不是重复代码，是两条不能合并的语义**（M17）。`TreeUtil.flatten()` 受
  折叠影响（渲染 / 键盘 / 滚动范围），`index()` 不受影响（级联 / 祖先链 / 后代集）。
  合并的代价不是性能，是**「折叠会悄悄改变勾选结果」**。
- **勾选集合只存"完全选中"**（M17）。不变量是「父在集合 ⟺ 所有直接子都在集合」，
  半选由 `subtreeHasChecked` **推导**、一个字节都不写进集合。于是"点半选的父"有唯一
  答案：它不在集合里 → `toggleSelected` 的判据只能是 `!isSelected(key)`。写成
  `!(isSelected || isIndeterminate)` 会把半选算成"要取消"，点一下变**整枝清空**。
- **回退键必须带纯结构路径，不能拿父「键」拼**（M17）。父键自带 `#` 前缀，拿它拼子
  路径会每层再叠一个（`#0` → `##0/0` → `###0/0/0`）。这类错误**自洽、不报错、能跑**，
  只有去读那个键的具体长相时才暴露 → 拆成 `parentKey` 与 `parentPath` 两个参数。
- **裸 `Item` 宿主 + `Repeater` 时，行的 `y` 必须自己声明**（M17 实测）。漏掉那一行
  之后，`visibleCount` / 每行 `key`·`level` 全对、8 条断言全绿，而屏幕上所有行
  **叠在第 0 行**上糊成一团。

**浮层 · 抓图**

- **浮层高度优先信宿主上报的 `contentHeight`**（M5）。等高条目时按「行数 × 行高」
  估算就够精确；菜单里有分隔线这类不等高条目，宿主最清楚每行多高 → 外壳先读
  `control.contentHeight`、读不到再估算。
- **`Popup` 未设 `parent` 时会被 Qt 挂到 `Overlay.overlay` 上**（M21 实测）。于是
  `Item.grabToImage()` 抓自己的子树时**一个浮层都不会进图** —— 首次核验的十条失败里
  A/B/D 全在量页底。抓图载体的选择见上一节「抓图载体三选一」（M31 复测，
  **那里的结论更新、带实测报错原文，以它为准**）。
- **抓图屏必须钉死输入**（M20 补测）。`QSkinInputOTP` 的"哪一格亮着"读的是
  `input.activeFocus` —— 窗口的键盘焦点，而抓图屏从来没接管过它 → 同一份抓图屏
  前后拍出**品牌蓝聚焦边框**与**灰边框**，差 480 像素 / 最大通道差 220 阶，而当时
  七组判据量的都是格宽 / 步长 / 几何，**两种状态都通过**。修法是把焦点交给一个
  **0×0 的惰性承载者**（`Item { focus: true }`）。
  ⚠ 一条错路：`otp.forceActiveFocus()` **更坏** —— 它点亮了输入框的**光标闪烁**，
  而闪烁是**读时间**的输入，正是"抓图要确定性"要关掉的那一类。
- **判"浮层墨迹"的门槛必须比噪声台阶小**（M21 实测，只在暗色下成立）。暗色页底是
  纯色、阴影边沿只暗 1~2 阶，所以 `POPUP_INK = 1` 而 `NOISE = 2`。门槛一旦回到 2，
  最外两像素被丢掉 → 宽度恒少 3px、顶边恒低 2px。**浅色四张全绿**，只有暗色能发现。

**槽位与派生量**

- **`Slots.install` 按白名单索引，键名写错是静默的**（M19.1）。四家主题写的
  `tdSpinRing:` 这类前缀键会被安静丢掉，而 `Slots.spinRing` 在四家下**都不是
  null**（它是 Basic 的）—— 于是"非 null"这种断言永远抓不到它。抓得住的是
  「装上去的必须 **≠** Basic」+「带着这一家的形态参数」。
- **同一格插槽的"设计分歧"未必是**可观测**的**（M20 实测，一枪变异逃逸打出来的）。
  `SCToggleBackground` 主张"开态铺中性灰而非品牌浅底"，可 shadcn 没有品牌色、
  `brandSubtle = bgSunken` 是同一个数 —— 把那一行换掉，屏幕上、截图上、属性上
  一模一样。**文件头里的对照表是意图，能不能被测出来要另算。**
- **一个属性值同时决定"哪一格可见"和"哪一格不可见"时，把它提成公开派生**（M19）。
  `QSkinEmpty.hasCustomArt` 就是这么来的 —— 它让属性侧能对**两个方向**各立一条断言，
  而不用等下一次抓图。

**核验本身（这一族最贵）**

- **断言测的是「属性值」，不是「渲染结果」**（M14 实测）。互斥断言一直全绿，而界面上
  树形模式仍在渲染勾选框 —— 6 处渲染点里有 1 处漏用了那个判据。**只要有一处渲染点
  绕过判据，断言就永远绿。**
- **断言可能在"它跑的那档输入"下根本区分不了对错**（M21 实测）。`[7]` 声称"通知卡
  底色跟着令牌走"，但只在**浅色**下跑，而浅色的 `bgElevated` 恰好就是 `#FFFFFF` ——
  把实现写死成 `"#FFFFFF"` 是**数值空操作**。自检法：先问"**如果实现退化成最蠢的
  写法，这条断言会红吗？**"答不上来 = 它只是一句注释。
- **判据里的比例门槛不能挂在一个会被无关量抬高的分母上**（M20 实测，加暗色实拍才
  暴露）。`dd > 0.06 * Dmax` 里 `Dmax` 是"maxr 内离圆心色最远的那个色"，暗色下
  **页底色**比外圈内壁还远，把 Dmax 抬了一倍，门槛跟着抬高。
- **代表图只在「核验器」这个意义上可复现，逐字节不是判据**（M20）。连拍四次同一场景
  出现**三种 md5**，差异是 **3 个像素、1 个灰阶** —— 那是**仪器噪声**，不是内容差异。
  所以判据要落在 `NOISE = 2` 这个中间档（"逐字节相等"太严，"看起来一样"太松）。
- **核验脚本的取样方法本身要先被质疑**（M12 / M13 两次踩到）。"分隔线只到 375.3"
  看着像横滚 bug，实为不同 `scroll` 位置用**同一设备行号**取样的假象；而 1 设备像素
  高的分隔线还会被 `int(yl * 1.5)` 的步进取样整条跳过。**探针证明"数值全对"之后，
  下一步查测量方法。**
- **抓图脚本自己也是被测对象**（M17）。第一版没摆悬停行，而物理鼠标恰好落在某一行上
  —— 每张图里都有一行灰底，且那个灰和 `disabled` 的灰同属一个底色家族，读图的人会
  把它当成"这行也被禁用了"。**"图看起来对"不算数，要能说清每一个像素是谁画上去的。**

17. **「全套自动化全绿」不等于界面画对了 —— 绿灯自己会骗你**（2026-10-03 实录）。
    `lint` 15 段（含三道令牌规则）、`test`（冒烟 48 + 两道像素门 + 运行期警告门
    + 五宿主对账 0x00）**全过**，而 `Arc` 主题在**深色**下灰色实心按钮
    **没有底色**。人工跑一次 `./tools/run.sh HelloQSkin` 才从日志里捞到：

    ```
    ACButtonBackground.qml:51:5: Unable to assign [undefined] to QColor
    ```

    根因是 `src/themes/arco/tokens.js` 的 `fillHover` / `fillActive`
    **只在 light 段有**。`Rectangle.color` 拿到 undefined 时**不回退成别的色，
    是这一帧不画** —— 视觉上就是"按钮不见了"。

    **为什么三道令牌规则都没抓到**：它们的解析器
    （`tools/check-tokens.py` 的 `parse_tokens`）用
    `out.setdefault(group, {})` 把 light / dark 两段**合并进同一个组**。
    「dark 缺某个键」这件事在合并结果里**不存在**，三条规则查的都是合并后的
    集合 —— **这不是漏了一条规则，是结构性看不见**。已改成
    `parse_tokens(path, by_mode=True)` 分开解析，并加规则 [D]：
    `dark` 段的 `color` 必须覆盖 `light` 的每一个键。

    两条要记住的：
    - **判据写在「合并之后的集合」上时，"某个来源缺东西"这类问题会永久隐身。**
      写判据前先问：*这个东西是在哪个来源里定义的？合并之后就答不了了。*
    - **无头抓图只跑浅色场景，就等于没跑深色。** 像素门再严，也得先有个
      深色 + hover 态的场景进用例集。

18. **文档里的数字会漂，而且没人喊**（2026-10-03 实录）。面向外部读者的
    文档有 5 份（README / COVERAGE / CHANGELOG / PITFALLS / GITHUB），
    读数**全是手写的**。手工核对一次就抓到四处：
    同一份 README 里「**11 道**脚本门」与「**9 道**」并存；架构图写
    「每套主题 = 1 份 token + **5 组**插槽实现」而实测四家是 **8/10/8/11**
    （同一份 README 另一处写的是正确的「若干插槽实现」）；新写的
    `docs/GITHUB.md` 压根不在**发布面泄露门**的扫描面里。

    根因是同一个：**手写的数字必然漂**。已有 `COVERAGE.md` 里那些
    「复算命令」也不够 —— 命令在那儿，**跑的是人**。

    解法是 `tools/check-doc-readout.py`（lint 第 16 段）：**从源码复算真值
    → 逐份发布面文档对账**。9 项读数。证伪 5/6 咬住、零假红。

    写这道门时踩的四个坑（比门本身更值得记）：

    - **只验「文档里有真值」是不够的。** 第一版这么写，证伪时把 `92` 改成
      `93`，**门照样绿** —— 因为 92 在别处还写着，而 **93 这个错数根本
      没人检查**。⇒ 必须同时验「**没有错的**」（±1 近值判据）。
    - **拿今天的标准去 judge 昨天的记录 = 逼着人改历史。** 逐处核对一开，
      报「CHANGELOG 里 4 处同量级读数只有 2 处对」—— 而那几条**全都是对的**
      （M33 当时的门数、当时的警告条数）。⇒ 历史文档只在「该数出现过」
      里参与，逐处核对必须排除。
    - **同量级的读数会互相污染。** `105 个类型` 与 `103 个公开类型` 是两条
      合法读数，只差 2；`12 道门禁` 与插槽区间 `8~11` 的**上界 11** 也撞。
      不做邻居表就互相判成「近似值」。⇒ 邻居要**逐对声明**，不能自动算
      （自动算会全列成邻居，门等于关掉）。
    - **区间型读数（`8~11`）只能做「字面量必须出现」**，不能逐处核对 ——
      区间里的每个数字在文档里都有合法的分项用途（COVERAGE 里
      「arco 有 8 个插槽」就是其中之一）。

    门数口径另踩一次：`grep -oE "tools/check-.*"` 数出 **18**（把 .sh 包装器
    与它 exec 的 .py 各算一次，还把 `gen-contract-manifest.py` /
    `qml-downgrade.py` 这类**被门调用的工具**算进去）。正确口径 =
    `grep -cE '^\w*SCAN=' tools/lint.sh` ⇒ **12**。注意 `\w+_SCAN=` 也不对
    —— 字符图标那道门的变量就叫 `SCAN`，没有前缀下划线。

**其它**

- **段高必须取整，且断言的参照系不能是同一套浮点公式**（M11.1 实测）。
  `cellSize * 0.9` 这类非整数高度在 `anchors` 链式堆叠里会被逐段舍入，累积把最后一行
  挤出可视区；而当时的几何断言比的是同一套浮点公式，于是"通过"了 —— **拿错误验证错误**。
- **`Component` 放进 Layout（`QSkinRow` / `Row`）会被当成待布局子项**（M11.1 实测）。
  `Loader { sourceComponent: ... }` 拿不到可视内容，且不报错 → 视觉片段要么定义在
  Layout 之外，要么直接内联。
- **浮层的「边缘渐隐」不是通用做法**。渐隐色取自面板底色，白底主题下等于没画、深色下
  深浅不一，提示强度完全不可控 → "这里还能滚"改用**前景元素**（选中行上下各一条
  品牌色细线）更稳。
- **`QSkinList` 的空态宽度不能用外宽算**（M19 实测）。`textMaxWidth` 吃的是**可用宽**，
  用 `root.width` 会在 320 > 280 时溢出 40px；但也不能用 `emptyBox.width` —— 空态块的
  隐式宽又喂回 `shell` 的隐式宽，读子项宽度会成**绑定环**。正解是纯函数式派生
  `_emptyAvailW`（只依赖 root 自己的属性）。
- **inline Component 之间 id 不互通**（M5 实测）。两个 delegate 各有各的声明作用域，
  A 里引用 B 实例的 id 运行时**静默失败**（无报错、内容空白）→ 跨 delegate 传数据要么
  走 `parent` 链（Repeater 会把 delegate 挂到宿主上），要么经文件级 id 中转。
- **Qt 5.11 的版本上界是实测出来的，不是「5.11 对应 2.11」**（Qt 5.11 档实测）。
  `QtQuick.Controls` 的**上界是 2.4**（5.11 的 `qml/` 下只有 `Controls.2` 一个目录，
  2.5 起全部 `module … is not installed`）；而 `QtQuick` 2.11 / `Layouts` 1.11 /
  `QtGraphicalEffects` **1.0** 可用。按直觉把 2.15 一律映射成 2.11，会让 33 个控件
  在真引擎上**加载期就崩**，而所有生成器计数账照样全绿。
- **`QtQuick.Shapes` 在 5.11 上是可用的**（实测 Shape / ShapePath / PathLine /
  PathAngleArc / PathSvg / dashPattern / Shape.opacity 全部 rc=0），只有
  `preferredRendererType` 不支持。原先「5.11 没有 Shapes、162 处路径要重写」的判断
  **是错的** —— 凭印象估工程量，差点把项目推向一次没必要的大改造。
  ⇒ **能力承诺必须有跑起来的宿主**，不能靠记忆或文档措辞推断。
- **5.11 的守卫不能用 `x !== undefined`**（实测）。`readonly property var _corners:`
  的值是函数调用，5.11 在它返回前就求值 `radius` ⇒ 每帧 `ReferenceError`。
  而守卫写成 `_corners !== undefined ? … : 0` **无效**：对尚未声明完的属性做
  `!== undefined`，守卫自己先抛 ReferenceError。正解是**真值判断** `c ? … : 0`。
- **`qml.exe` 会把错误日志吞掉，`qmlscene` 不会**（实测）。5.11 的 `qml.exe` 失败时
  只回 `Did not load any objects, exiting.` 且 **rc=0**；`qmlscene` 才给
  `file:///…:1871 Expected token \`identifier'` 这种带行号的真错误。
  ⇒ 诊断一律用 qmlscene；跑期错误还要加 `QT_FORCE_STDERR_LOGGING=1` 才看得见。
- **`.qmlc` / `.jsc` 是引擎缓存，不是产物**（实测）。跑一次 qmlscene/qml.exe 就生成；
  Qt 5.11 验证后 `qt511/` 多出 178 个 `.qmlc` + 10 个 `.jsc`（而 `qt5/` 保持 0 个）。
  它们与平台/编译器绑定，若不排除，漂移门会被 188 条「残留」噪声淹没 ——
  实测 `--check` 因此误报 215 处漂移而真问题一个没有。已加进 `.gitignore`（第 24–25 行）
  并在 `snapshot()` 里排除。
- **「提取块 → 改写 → 放回」会吃掉块前缀**（Qt 5.11 档实测，同一类错犯了两次）。
  `_extract_block` 返回的是**从 `{` 开始**的块，直接拼回去就丢了
  `gradient: ` / `Popup ` 这类前缀，产物里剩下孤零零的 `{`。
  ⇒ 已抽 `_replace_block_keep_prefix()`，前缀只在一个地方拼。
- **`TextMetrics` 有三个宽度口径，混用会让「逐字累加」凭空少几十 px**
  （TextMetricsUtil 实测）。`width` 是**包围盒**（含左右 side bearing）、
  `advanceWidth` 才是**排版真正用的前进宽度**、`tightBoundingRect` 是紧包围盒。
  引擎排版按 `advanceWidth` 累加 ⇒ 逐字加必须用它。用 `width` 的实测后果：
  「布局语义搬进 QML，」@px24 整串一次量 205.25px、逐字累加 177.34px，
  **少 27.91px** ⇒ 贪心多塞进一个字 ⇒ 那一行比引擎宽 ⇒ **大字号下差一行**，
  而调余量（扫 0~2.5% 全部）救不回来。
- **自然行高要 `ceil`，`round` 只在默认字体下偶然成立**（同上实测）。
  换到 Segoe UI 就错。另一处错更隐蔽：**高度对照组当时用了不同字体** ——
  拿两套字体互比，测试本身就是错的。⇒ 判据必须与被测对象**同字体**。
- **降级产物的 import 版本号只对它那一档成立**（实测踩过）：
  `qt5/` 里保留 `import QtQuick 2.15` 是**对的**（5.15 的最高版本就是 2.15），
  拿它去喂 5.11 会报 `module "QtQuick" version 2.15 is not installed`。
  ⚠ 这类"看起来像漏改"的东西**不能靠 grep 判**——我一度以为 182 个文件
  全没降级，实际是**测试用错了档**。验产物必须先确认档位对应关系。
- ⚠⚠ **`counters[key] += n_hit` 是函数末尾才加的** ⇒ 回调里读到的计数
  **在同一文件所有命中处都相同**（Qt 5.11 档实测）。我用它给四角圆角
  降级插入的 `QtObject` 拼 id ⇒ 两处都叫 `_c511_12` ⇒ QML 报
  `id is not unique` ⇒ `TDInputBackground` **加载期就失败** ⇒ `TDesign`
  整个类型 unavailable ⇒ 3 个示例页 + 深色场景全挂。
  ⇒ 正解：`repl_in_code` 给回调追加一个**块序号**参数（本次调用内的命中序号），
  用它唯一化。⚠ 改回调签名要用 `__code__.co_argcount` 探测，
  **别用 try/except TypeError**（回调内部自己抛的会被误判成签名不匹配）。
- ⚠⚠⚠ **中文在 Qt 5.11 上渲染成豆腐块，而引擎零报错**（实测）。
  Qt 5.11 官方二进制**不自带字体**；系统装了雅黑、但 Qt 只认自己的
  `lib/fonts/` ⇒ 找不到 `Microsoft YaHei` ⇒ 回退到无中文字形的字体
  ⇒ **每一页的中文全是空心方框**，而 `qml.exe` rc=0、`qmlscene` 也只报
  无关的 OpenGL 提示。⚠ 库的字体声明是对的，**不是库的 bug，是环境缺字体**。
  ⇒ 这类问题**只有从渲染结果里量才能发现**，和控制台无关
  （与「深色没测」同一性质：渲染侧的事只能从渲染侧看）。
- ⚠ **「唯一色数 ≥ 固定阈值」这种判据会假红**（实测踩过）。
  我用「唯一色 ≥ 300 ⇒ 中文字体可用」，理由是另一个场景有 327 色 ——
  但换个场景只有 244 色，图里中文**明明正常**。
  ⇒ 跨场景拿绝对量比较必然出错。正解是**同一场景跑两遍**
  （有中文字体 / 挪走中文字体），比**前景像素数比值**。
  实测比值 3392:2512 = **1.35**（不是 2~3 —— 拉丁字符两遍都画得出来，
  把比值稀释了），阈值取 1.25。
